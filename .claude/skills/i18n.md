# Internationalization (i18n) Skill

## When to use

Always apply these rules when adding, modifying, or reviewing any user-facing text in this application (labels, buttons, messages, placeholders, errors, tooltips, titles, etc.).

## How this project handles translations

This app uses **react-i18next** with three languages: English (`en`), Spanish (`es`), and French (`fr`).

- Translation files: `src/locale/i18n/en.json`, `src/locale/i18n/es.json`, `src/locale/i18n/fr.json`
- i18n setup: `src/locale/i18n/getI18n.ts`
- Translations are organized by namespace keys (e.g., `button.add`, `messages.loading`, `title.scores`)

## Rules

1. **Never hardcode user-facing strings.** Every visible string must use a translation key via `useTranslation()` or the `t()` function.

2. **Always add the key to all three language files** (`en.json`, `es.json`, `fr.json`). If you don't know the correct Spanish or French translation, add the English text as a placeholder and leave a comment noting it needs translation.

3. **Use the `useTranslation` hook** in React components:
   ```tsx
   import { useTranslation } from 'react-i18next';

   const MyComponent = () => {
     const { t } = useTranslation();
     return <button>{t('button.confirm')}</button>;
   };
   ```

4. **Use interpolation** for dynamic values instead of string concatenation:
   ```tsx
   // Correct
   t('placeholder.score', { score: 42 })

   // Wrong
   `${t('placeholder.score')}: 42`
   ```

5. **Follow the existing key structure.** The translation files are organized into these namespaces:
   - `aria` - Accessibility labels
   - `title` - Dialog and section titles
   - `button` - Button labels
   - `placeholder` - Input placeholders and formatted display strings
   - `messages` - Informational and confirmation messages
   - `navigation` - Navigation tab labels
   - `errors` - Validation and error messages
   - `text` - Longer descriptive text blocks
   - `skins` - Theme names

   Place new keys under the most appropriate existing namespace, or create a new one only if none fits.

6. **Keep keys descriptive and consistent** with the existing naming convention (camelCase within dot-separated namespaces).
